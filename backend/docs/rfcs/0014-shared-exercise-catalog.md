# RFC 0014 — A shared exercise catalog for guests and signed-in users

**Status** Proposed · **Date** 2026-11-17 · **Scope** Exercise discovery, guest workout logging, and Google sign-in

## Product decision

Anyone should be able to open the picker, find a released exercise, log sets, and finish a workout. Give guests and signed-in users the same online catalog, search, muscle filters, and pagination. Keep guest workouts on the device across reloads. After a guest finishes a workout, offer **“Sign in with Google for your free AI recap”** alongside the option to finish as a guest. Tracking and AI coaching both remain free.

The seeded catalog originated as part of offline logging. End-to-end offline logging has already stopped working reliably. Maintaining a separate picker now limits the exercises guests can find without delivering that original benefit. This proposal retires the seed for new guests. Restoring end-to-end offline logging would be a separate decision.

## Share catalog reads and preserve local workouts

The [catalog endpoint](../../src/exercises/router.py) accepts an optional user today. The [picker results hook](../../../pe-be-tracker-frontend/src/features/exercises/hooks/useExerciseTypeModalResults.ts) enables server queries only for authenticated users and separately filters guest records. The [guest initializer](../../../pe-be-tracker-frontend/src/stores/guestStoreSeedData.ts) generates exercise type IDs and seeds the browser.

| Action | Guest | Signed in |
| --- | --- | --- |
| Browse and search | All released exercises from the API | Same API, with existing visibility rules for the user's own types |
| Log a public exercise | Save its server ID as a string and a display snapshot with the local workout | Save through the workout API |
| Create a custom exercise | Keep a local ID and definition, reusable in later workouts on this device | Use the existing authenticated creation flow |
| Finish a workout | Save locally and offer Google sign-in for a free recap | Use the existing recap flow |

Use the existing browse and search queries in both sessions. Keep visibility-sensitive results scoped to the current session or account, including retained search results on sign-out. Use API muscle groups and pagination. Show loading, retry, and empty states consistently. A catalog request failure must leave the open workout and its logged sets intact.

Keep guest-created types accessible in a small *My exercises* list in the picker. Search can match those local names alongside server results. This list contains only the guest's own definitions. Public selections need a display snapshot for workout history, but selecting a public type should never add a second searchable catalog entry. Keep workout-type initialization unchanged.

- If browse, search, or the exact lookup fails, show **Retry** wired to the failed request. ### Logging a guest selection

Both the workout card picker and `ExerciseForm` should pass the selected object directly to the guest write. Looking up a public result in `guestData.exerciseTypes` would discard a valid selection. Store the ID as a string and use a shared snapshot mapper that preserves name, equipment, default intensity unit, guest-visible images, and muscles including each nested `muscle_group.name`. This lets the finish modal compute muscle totals and history render thumbnails after reload. Increment local `times_used` only for a local custom selection. Any optimistic usage update for a public result belongs in the viewer's query cache. ### Thumbnails in guest results

The asset route requires sign-in for `generated/` paths, and the URL resolver can return those paths. Before enabling the guest picker, inspect image URLs returned for released types in anonymous browse and search. For generated artwork approved for public display, serve the corresponding published asset through the existing publication path. When a released type has only a private image, omit its URL from the anonymous response and render the picker's no-image state. Keep access controls on generated originals and candidate uploads. ### Existing devices and Google sign-in

- Stop generating exercise seeds on fresh installs. In the v5 → v6 guest-store migration, tag new custom definitions explicitly. For v5 records compare the full seed definition (name, description, default unit, and other descriptive fields) against the frozen v5 seed list, ignoring generated IDs and usage counts. Exact seed matches stay out of *My exercises*. Keep custom and edited definitions selectable under their original IDs, including records with the creation flow's “Custom exercise” description. For indistinguishable exact matches, retain the definition for historical resolution. This comparison classifies legacy picker entries only and never assigns a server ID. [v5 seeds](../../../pe-be-tracker-frontend/src/stores/seeds/exerciseTypes.ts)
- Build the sync payload from the submitted workout references. Resolve local IDs from their definitions or embedded exercise snapshots, preserving names and units. Include a legacy seed definition only when referenced. Retain definitions and snapshots referenced by local routines. Opening the upgraded picker or signing in must never import the entire seed list as private candidates.
- Match catalog selections by explicit server exercise-type ID only. Validate both direct IDs and legacy external IDs against released-or-owned visibility. Remove the exercise-type `ilike(guest_et.name)` fallback. A local definition whose name and description exactly match a v5 seed, under its current or pre-#443 name, maps to the released type with that catalog name, since seeds never carried a server ID; the frozen list lives in the import service. Otherwise, for a new local ID without a server ID, create a private candidate for the signing-in user. If candidate creation hits the owner’s candidate or in-review unique-name constraint, find the conflicting type by exact `lower(name)` equality. Return its ID and display name alongside the local type ID, roll back the import, and retain the local data. Let the user explicitly select the existing private type or rename the local definition under the same local ID. On retry, validate that the selected type is still owned by the account, or create a private candidate with the new name. Persist the chosen server ID against the account and local type ID in the same transaction as the completed import. Treat names (including `%` and `_`) as literal labels. [Bulk import service](../../src/sync/service.py) · [Exercise type constraints](../../src/exercises/models.py)
- An unresolved or inaccessible exercise ID must leave its workout recoverable. Today the server can skip an exercise and the client can clear the guest store after a successful response. Roll back an incomplete bulk import and retain the local data for retry. [Sync client](../../../pe-be-tracker-frontend/src/utils/syncGuestData.ts)
- Collect distinct numeric exercise-type IDs from submitted workouts and legacy external IDs, then resolve the set in one released-or-owned batch query before the workout loop. Reuse the lookup for repeated selections and report unresolved references before committing.
- Replace the guest store's full `clear()` callback with targeted cleanup against the submitted snapshot and the latest store state. At dispatch, capture an immutable snapshot of each full persisted guest workout, including its ordered exercises, sets, and local fields. During cleanup, remove a mapped workout only if its current persisted value is deeply equal to that snapshot, comparing object fields by value and arrays in order. Preserve workouts created or edited during sync, routines (which the bulk payload omits), reusable custom definitions, and exercise or workout types referenced by remaining records. If a workout changes during sync, keep it local and apply the edited version to the mapped server workout. Wait for the server to confirm the saved edits, then check that the current local record still equals the version whose edits were confirmed before removing it or marking it imported. A fresh local snapshot or a replay that only returns the existing mapping cannot confirm those edits. If the update fails or the workout changes again, keep the local record for reconciliation. [Guest store](../../../pe-be-tracker-frontend/src/stores/useGuestStore.ts)

### Workout IDs on import and retry

The current duplicate check skips a workout when the owner and `start_time` match. Two distinct workouts can share that timestamp. Persist a mapping from `(user_id, guest_workout_id)` to the server workout ID in the same transaction as the workout, exercises, and sets. Enforce uniqueness on the mapping key. Two distinct guest IDs with the same start time each create their own workout. A repeat of the same guest ID, including a concurrent retry, returns the committed workout ID and creates no additional rows. Historical imports lack this mapping. A timestamp collision with an unmapped legacy workout is insufficient evidence to link the two.

Extend the backend and frontend `SyncResult` with `workoutIdMap: Record<string, number>`. Every successful import includes an entry for every submitted workout, including previously imported ones. The duplicate branch adds the existing ID to the map before continuing. Keep the existing count fields. Build every response map, including idempotency-key replays and retries after a concurrent request wins, from the per-workout mapping; the sync log stores counts and a SHA-256 fingerprint of the request payload. A key replayed with a different payload fails, even when its workouts are already mapped. Logs written before this change have no fingerprint, so replaying one of their keys returns an unconfirmed failure, even when the submitted workouts are already mapped; an account-level mapping proves a workout exists, not which request created the key. When a counts-only replay leaves the original import unconfirmed, pause automatic retries for the affected workouts and keep their local data. Recover the original server workout only when durable evidence independently links it to that guest workout, such as an import record that explicitly records both IDs. Verify account ownership and persist the recovered mapping before resuming. A fresh key may replay a recovered mapping, but must not create a workout as part of legacy recovery or use a newly created mapping to confirm the original import. If the original workout cannot be identified, leave the import unresolved and retain the local workout. A timestamp or matching workout content alone cannot establish identity. [Response schema](../../src/sync/schemas.py) · [Per-workout mapping](../../src/sync/models.py)

Ship one inspector-guarded Alembic migration that creates `guest_workout_mappings` and `guest_exercise_type_mappings` and adds a nullable `sync_logs.request_fingerprint` column. Existing logs keep a null fingerprint. Exercise upgrade, downgrade, and re-upgrade on a disposable copy of representative production data. Verify that pre-existing workouts, exercises, sets, and sync-log counts survive each step. Downgrade drops both mapping tables and the fingerprint column. That loses every guest-ID → server-ID mapping, so a later retry can import an already-imported workout again, and replayed keys stop being bound to their payloads. Back up both mapping tables before a production rollback that must keep this protection.

### From the finish button to the recap

1. The recap CTA finishes the local workout and awaits the guest-store flush. On success, save a tab-scoped recap intent containing the guest workout ID in session storage before starting Google OAuth. Skip the finish handler's usual navigation to `/workouts` for this action. Finishing as a guest keeps that navigation. A returning guest can reload the app, open the finished workout from workout history at `/workouts/{guest_id}`, and choose the same CTA. Record that workout's ID and start OAuth without finishing it again or changing its saved end time. Ordinary sign-in follows the existing post-login destination. [Finish handler](../../../pe-be-tracker-frontend/src/features/workouts/hooks/useWorkoutExerciseActions.ts)
2. After OAuth, `usePostLoginCompletion` confirms the account and awaits the structured sync result. Change `syncWithServer()` to return that result and share it with any sync already started by the store initializer. Persist the resolved server ID and account alongside the pending intent before guest cleanup, so a callback reload can resume even if the local workout is gone. If sync fails or the map omits a submitted ID, keep the local records and offer retry. [Post-login callback](../../../pe-be-tracker-frontend/src/features/auth/hooks/usePostLoginCompletion.ts)
3. Replace the callback route with `/workouts/{server_id}`. On that detail page, consume the intent only for the matching account and workout. If a recap already exists, display it. Otherwise automatically call `POST /api/v1/workouts/{server_id}/recap` and show progress. Mark the request as started before dispatch so a remount cannot submit it again. Treat generation as successful when the workout response contains a saved recap. If the response has no recap, including on HTTP 2xx, or the request fails or is interrupted, keep the intent and reload the workout. Offer an explicit retry if the reloaded workout still has no recap. Clear the intent only when a saved recap is present, the user cancels, or the account changes. [Recap endpoint](../../src/workouts/router.py)

## Release and acceptance

Deploy the import changes first, then switch the picker to the shared catalog and stop generating exercise seeds.

- On a fresh device, find a released exercise absent from the old seed, log it alongside a custom exercise, reload, and finish as a guest. Sign in with Google and verify the recap belongs to that workout.
- On an existing device, verify that exercise names, units, sets, and routines survive hydration and a failed import. Retry after a lost response and verify the workout appears once.
- Import two guest workouts with different IDs and identical start times. Verify they get distinct server IDs and the selected workout gets the recap. Replay the request with the same key and then a fresh key. Both must return the original mappings, with no extra workouts, sets, or custom types.
- Import local types named `Bench`, `%`, and `_` alongside a released `Bench`. Verify each local ID resolves to its own private candidate and a selection carrying the released ID still resolves to the public type.
- Fetch released-type results as a signed-out user and request their actual thumbnail URLs without cookies. Verify published images load, a generated-only private reference renders the no-image state, and the protected original still requires sign-in.
- Exercise search, clear the query, and select a result. Change muscle filters while loading, paginate, and retry a failed request. After sign-out, verify that private results from the previous account disappear.
- Exercise the OAuth redirect and callback reload with two finished guest workouts and initializer sync enabled. Verify the CTA lands on the selected server workout, sends one automatic recap request, and offers retry after a failure. Ordinary Google sign-in should generate no recap.
- Migrate a v5 fixture containing unchanged seeds, a used seed, a modified seed, a custom type, and a routine reference. Verify picker membership, historical display, and the precise definitions submitted to sync. Log a public result through both entry points and verify muscle totals and thumbnails after reload.
- Warm the picker as a guest, switch between two accounts with private results while search is pending, then sign out. Verify the new viewer never sees or selects retained private results. Search for a type hidden by a muscle filter, then repeat with a failed lookup and exercise both Retry and local creation.
- Sync a payload with repeated public exercise IDs and verify a single visibility lookup for those IDs. Add a workout while the request is in flight and check that cleanup preserves it, a local routine, and their dependencies. Repeat with a routine-only device.

Evaluate the product change with completed first workouts per new visitor and the share of guests who receive a recap after choosing Google sign-in. Track catalog request failures and incomplete imports separately so a failed handoff is distinguishable from someone choosing to keep logging as a guest.
